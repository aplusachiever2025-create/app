# SG Tutor Match — 纯文件存储版可行性与实施方案

状态：讨论稿 / 独立 staging。不会修改 main、正式网站或现有 Supabase 项目。

## 结论
技术上可行：使用 PHP + JSON 文件保存业务数据，不运行 MySQL，也不调用 Supabase。推荐只用于原型、小规模试点或低并发内部运营。由于 Tutor Match 保存联系方式、老师履历、配对状态和佣金记录，纯文件版的并发一致性、查询、权限、备份恢复风险明显高于数据库方案。若长期运营规模增长，应保留迁移到数据库的接口设计。

## 目标结构
- 前台：HTML/CSS/JS。
- 后端：PHP JSON API。
- 数据：私有目录内的 JSON 文件，不能放在可直接通过 URL 下载的位置。
- 上传：私有履历目录；文件随机命名、限制 MIME/大小、禁止脚本执行；仅经过管理员权限验证的 PHP endpoint 可下载。
- 身份验证：管理员账号数据文件存储 password_hash() 哈希；登录后使用 PHP session、session ID 轮换、安全 cookie、登录限速、CSRF token 和权限校验。
- 备份：定时/人工加密备份，保留多个版本，定期验证能否恢复。备份不与实时数据放在同一个可公开目录。

## 推荐文件布局（示例）
public_html/tutormatch-file/       # 仅放可公开页面和入口 API

  admin.html
  api/index.php
  .htaccess                       # 禁止访问配置、日志、备份等敏感路径
/home/ACCOUNT/tm-private/          # 仅示意；实际路径需在 cPanel 验证
  config.php
  data/
    parents.json
    tutors.json
    interests.json
    cases.json
    case-notes.json
    admins.json
    audit-log.jsonl
  resumes/
  backups/

必须确认真实主机的 home 路径与目录权限，不能照抄示例路径。若无法在 web root 外写文件，则必须先设计并验证强制拒绝直接访问的服务器规则，不能把敏感 JSON 暴露在公开目录。

## JSON 记录约定
- 每条记录有稳定 UUID、created_at、updated_at、状态和 schema_version。
- 联系方式、内部评分、跟进记录、佣金与履历元数据不出现在公开响应中。
- JSON 文件损坏时 API 失败关闭，不得自动覆盖成空数组。
- 所有写入：校验输入 -> 对相关文件加 LOCK_EX/共享锁策略 -> 读取并验证 schema -> 更新 -> 写入临时文件 -> 原子 rename -> 记录审计事件。
- 跨多个文件的业务事务很难可靠实现。配对创建、成交确认、关闭家长需求和佣金记录等操作应尽量设计成单个聚合文件一次原子写入，或使用可恢复的操作日志与幂等 ID；仍须明确记录文件方案的限制。
- 禁止依赖前端隐藏按钮作为权限保护；所有权限在 PHP 服务端验证。
- 不记录明文密码、完整联系信息或文件内容到错误日志。

## Tutor Match 必须实现的业务
1. 家长需求：科目、年级、预算、授课模式、地区/邮区、时间、联系方式和 request 状态。
2. 老师资料：统一科目与年级词典、费率、地区、时间、教学模式、老师状态、可选履历。
3. 规范科目映射：家长和老师端共用一套 canonical subject/level 字典；覆盖 Primary、Secondary、IP1–IP4、JC1–JC2/A-Level、E-Math、A-Math、Combined Science、Social Studies、H2 Chemistry 等及其别名。
4. SmartMatch：核对科目、年级、预算、模式、地区和时间；不能仅凭字符串相似就配对。
5. 案件状态：待处理、双方有兴趣、沟通中、试听中、已确认、未成交、取消。
6. 成交逻辑：确认后关闭家长 request，但老师档案仍可继续接收其他家长的匹配。
7. 佣金：按两次课时费计算，保存费率、课时长度、每周节数（如有业务需要）和计算快照，避免后续资料修改导致历史金额变化。
8. 运营后台：待跟进、逾期、负责人工作量、转化漏斗、待处理数量、内部家长/老师质量评级。
9. 审计：记录管理员、时间、动作、目标 ID 和成功/失败结果。
10. 联系方式仅用于平台撮合，不向其他家长/老师公开。

## 主要风险
- 并发：两次同时提交可能丢更新或创建重复案件；锁和幂等键可缓解，但无法像事务型数据库一样简单可靠。
- 查询：随着数据增长，筛选与统计需遍历文件，响应速度可能下降。
- 一致性：家长需求、案件、佣金分散在多个文件时，某一步失败会留下部分更新。
- 损坏：写入中断或磁盘空间不足可能破坏 JSON；需要临时文件、原子替换、备份和恢复演练。
- 安全：目录误配置可能让个人联系方式或履历被直接下载。
- 备份：同一主机内的副本不能防止整个账号/主机故障。
- 共享主机限制：cron、权限、PHP 版本、可写目录和资源配额须在 cPanel 实测。

## 成本判断
- 不需单独购买 MySQL 数据库服务；若现有 Shared Hosting 已含主机空间，额外托管成本可能为零。
- 仍有开发、测试、维护、备份、监控与安全修复成本。纯文件不等于没有运维成本。
- 不能在未确认主机套餐、开发方式和数据量前承诺固定价格或零成本。

## 阶段与验收
Phase 1：建立独立分支和 staging 目录，检查 PHP、HTTPS、私有目录、写权限与上传限制。
Phase 2：先用假数据搭建 JSON repository 层、健康检查和读写测试；验证锁、原子写入、损坏处理、备份恢复。
Phase 3：管理员认证、权限、审计、CSRF 与限速。
Phase 4：家长/老师 CRUD 与隐私过滤。
Phase 5：科目规范化、SmartMatch、去重、案件状态机、成交和佣金逻辑。
Phase 6：履历私有上传/下载、运营驾驶舱。
Phase 7：用假数据进行并发、故障、权限、备份恢复和业务回归测试。
Phase 8：小规模试点；只有在验收并确认风险可接受后，才讨论生产切换。生产切换前备份现有数据，保留旧系统回滚路径。

## 建议的停用/升级条件
出现以下任一情况，应暂停纯文件方案并评估数据库：多名管理员频繁同时修改、重复/丢失记录无法可靠防止、统计查询明显变慢、审计或事务要求提高、业务量持续增长，或数据恢复测试不合格。
